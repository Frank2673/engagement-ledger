# 授权书接收与哈希登记操作手册

> 面向执行人。目标只有一个：**让"这份授权书此后没被人换过"成为可核验的事实**，
> 而不是一句口头保证。

## 这份手册解决什么

凭证里如果没有授权书哈希，审计时你能拿出的只有一句"授权书编号是 AUTH-2026-001"。
编号是一段文本，谁都能改；哈希不是。

| 没有哈希登记 | 有哈希登记 |
| --- | --- |
| 客户无法确认你依据的是他签的那一份 | 对归档副本算一次 SHA-256 即可比对 |
| 事后出现"范围更大的授权书"无从分辨 | 换过就必然对不上 |
| "我依据的是原始授权"只是陈述 | "我依据的是这份文件"是可以被验证的事实 |

**注意**：哈希登记只解决"文件有没有被换"。它**不**判断授权书本身是否真实、
签署人是否有权、范围是否恰当 —— 那些只有授权方能确认（见文末「能力边界」）。

---

## 一句话原则

> **先固定一份归档副本，此后只引用它，永不重新生成。**

你登记的不是"那份授权书"，而是"归档目录里的那一个文件"。
任何一个字节的差异（重新扫描、阅读器另存、补签名、加时间戳水印）都会让哈希失配。

---

## 第 0 步：确认这是一份"可登记的授权"

先别急着算哈希。逐条确认：

- [ ] 有**明确授权人**（姓名 + 职位 + 联系方式）
- [ ] 有**明确的授权日期**
- [ ] 写清了**资产清单**，而不是笼统的"某某公司的系统"
- [ ] 写清了**起止时间**
- [ ] 写清了**允许的动作**（很多授权书只允许扫描，不允许人工验证）
- [ ] 写清了**排除项**（支付系统、生产数据库往往是排除的）

任何一条打不上勾，先向授权方补齐。**把一份不合格的授权书登记成哈希，
只会让不合格的东西看起来更正式。**

---

## 第 1 步：按来源处理

### A. 电子签章 PDF（最理想）

直接归档即可。注意有些签署平台会在你不察觉时重新生成 PDF（例如"下载已完成文件"按钮
每次生成内容相同但元数据不同），所以**只下载一次**，之后用归档副本。

### B. 纸质签名的扫描件（常见，有坑）

扫描件**每次扫描的结果都不同**（扫描仪噪声、倾斜角度、分辨率设置）。
因此：

1. 扫描一次，确认清晰、完整、无缺页；
2. 立刻归档这一份；
3. **把纸质原件与扫描件一起存放**，并在凭证 `notes` 里注明原件的保管位置。

> 不要"为了更清楚再扫一遍"。更清楚的那一份哈希与凭证对不上，等于没有登记。

### C. 邮件授权（最需要小心）

邮件授权的证据力来自**头部信息**（发件人、时间、Message-ID），而这些信息在
打印成 PDF 时最容易丢失。推荐顺序：

1. **首选**：导出为 `.eml`（Outlook：另存为 → Outlook 邮件格式 `.msg`；
   更通用的是"另存为 .eml"或从邮件头导出）。
   `.eml` 保留了完整头部，是自包含的。
2. **次选**：打印为 PDF，但必须确认 PDF 里**包含发件人、收件人、发送时间**。
   很多邮件客户端的打印样式会把这些显示在页面顶部 —— 打印预览里先确认。
3. **两者都留**：`.eml` 作为证据本体，PDF 作为可读副本。**登记的是 `.eml`**。

如果授权只在邮件正文里（没有附件、没有签章），在凭证 `notes` 里写明这一点，
让报告的使用者知道证据形态。

---

## 第 2 步：归档

用仓库里的脚本一次做完"复制 + 算哈希 + 生成凭证片段"：

```bash
node scripts/intake-authorization.mjs "D:\往来\AUTH-2026-001 签署版.pdf" \
  --dir authorization --as AUTH-2026-001.pdf
```

预期输出：

```text
✅ 已归档授权书

  源文件　：D:\往来\AUTH-2026-001 签署版.pdf
  归档副本：D:\...\authorization\AUTH-2026-001.pdf
  大小　　：182,431 字节
  SHA-256 ：8c0b71f9b1abe2d9922500e6560ad5c87df4f8cb28b8cfb0ed277a9b4f6640e5

把下面两行填进凭证的 engagement.authorization：

    "document": "authorization/AUTH-2026-001.pdf",
    "documentSha256": "8c0b71f9b1abe2d9922500e6560ad5c87df4f8cb28b8cfb0ed277a9b4f6640e5"
```

不想直接复制文件时加 `--dry-run` 先看结果。需要程序化处理时加 `--json`。

**脚本会拒绝覆盖已存在的归档副本** —— 覆盖会作废已经登记进凭证的哈希。
脚本也不做真实性判断，它只固定文件。

> 没有这个脚本时，手工流程是：把文件复制到 `authorization/` →
> `node src/index.mjs hash-doc authorization/AUTH-2026-001.pdf` → 抄进凭证。
> 脚本存在的意义是消掉"手抄 64 位十六进制抄错"这个失败模式。

## 第 3 步：登记进凭证

```jsonc
{
  "engagement": {
    "authorization": {
      "reference": "AUTH-2026-001",
      "signedBy": "张示例",
      "signedTitle": "信息安全负责人",
      "signedAt": "2026-09-01",
      "document": "authorization/AUTH-2026-001.pdf",
      "documentSha256": "8c0b71f9b1abe2d9922500e6560ad5c87df4f8cb28b8cfb0ed277a9b4f6640e5"
    }
  }
}
```

**路径解析规则**：`document` 相对**凭证文件所在目录**，不是当前工作目录。
凭证放在仓库根、`authorization/` 也在仓库根时，上面这行可以直接用；
凭证在子目录（例如 `engagements/2026-001/engagement.json`）时，
要写成 `../../authorization/AUTH-2026-001.pdf`。

**归档副本通常不入版本控制**：它可能含客户机密与手写签名。
仓库的 `.gitignore` 默认排除 `authorization/`，只把哈希写进凭证 ——
这正是哈希存在的原因：文件不用共享，也能证明没被换过。
请把归档副本存到可靠位置（加密存储 / 受控目录）**并做好备份**。

---

## 第 4 步：核验

```bash
node src/index.mjs init --manifest engagement.json --ledger ledger.jsonl
```

期望看到：

```text
✅ 授权文件核验通过：授权书内容与登记哈希一致（8c0b71f9b1abe2d9…）
```

看到下面这行说明**填错了哈希或文件被动过**，先停下来查清楚，不要继续：

```text
⚠️  授权文件核验未通过：授权书内容与登记哈希**不一致**：登记 8c0b71f9… / 实际 a1b2c3d4…
```

`init` 在这种情况**不会失败**（告警而非阻断）—— 因为"文件不在本机"也是一种正常情形
（例如你在客户现场，归档副本在受控存储里）。但**报告里会一直带着这条告警**，
所以别放着不管。

---

## 第 5 步：让他人复核

把报告交给客户时，附带**一条命令**，而不是让他信任你：

```bash
node scripts/verify-report.mjs compliance-report.md "D:\授权\AUTH-2026-001.pdf"
```

输出与退出码：

```console
✅ 一致：报告所依据的授权书，就是你手上这一份

  委托编号　：ENG-2026-DEMO-001
  授权文件　：AUTH-2026-DEMO-001
  报告登记值：12cd1158dbe6b3ab67afc44a0ea8f897328a10b16c27c4400b19ce45233766ef
  你手上这份：12cd1158dbe6b3ab67afc44a0ea8f897328a10b16c27c4400b19ce45233766ef

结论：这份报告所引用的授权书与你的原件逐字节相同，授权范围描述可信。
      注意：这只证明"文件相同"，不证明授权书本身有效 —— 那由你方判断。
```

不一致时退 **3**，并给出排查顺序（是不是中途版本、是不是重新扫描过、是不是拿错了文件）：

```console
❌ 不一致：报告所依据的授权书，不是你手上这一份

  报告登记值：12cd1158dbe6b3ab67afc44a0ea8f897328a10b16c27c4400b19ce45233766ef
  你手上这份：91b5b416de564ffb6187c58411d68911ca03dc286bba7bca7168375e0d7fac15

**请先不要采信这份报告。** 依次排查：
  1. 你手上的是否为最终签署版？（常见于中途版本被拿去用）
  2. 文件是否被重新扫描、另存、补签名或加水印 —— 任何重新生成都会改变哈希
  3. 是否用错了文件（例如同名草稿）
  4. 以上都排除后，向交付方索要其归档副本，直接比对两份文件
```

**为什么要有这一步**：让客户自己跑 `Get-FileHash` 再肉眼比对 64 位十六进制，
成功率约等于零 —— 结果是复核环节变成走过场，或者抄错一位后误判。
这条命令把复核压缩成"看退出码"。加 `--json` 还能给客户的系统消费。

<details>
<summary>客户想自己算哈希（不使用本工具）</summary>

```powershell
# Windows
(Get-FileHash -Algorithm SHA256 "D:\授权\AUTH-2026-001.pdf").Hash.ToLower()
```

```bash
# macOS / Linux
shasum -a 256 AUTH-2026-001.pdf
```

拿到 64 位十六进制后，与报告第 1 章「授权文件完整性指纹」下的那一行逐字符比对。
</details>

这条可比对的指令，是"可核验"与"请相信我"之间的全部差别。

## 授权书变更怎么办

范围变更、延期、追加资产都是常态。**不要覆盖归档副本**，做法是：

1. 新授权书另起归档名（例：`AUTH-2026-001-20260915-延长至次年3月.pdf`）；
2. 在凭证里记录**一条 note 类型的日志**，说明谁在何时因何变更：

```bash
node src/index.mjs log --manifest engagement.json --ledger ledger.jsonl \
  --target example.com --action note --result "授权延期至 2027-03-31（补充函 AUTH-2026-001-2）" \
  --evidence "authorization/AUTH-2026-001-20260915.pdf"
```

   > 备注条目不需要通过校验门，但会进报告的动作流水，成为变更的可查痕迹。

3. 更新凭证的 `document` / `documentSha256`；
4. 重新 `init`？**不要**。`init` 只在日志尚不存在时可用。
   凭证变了不影响已有链 —— 链路记录的是"当时依据的凭证内容"，
   而报告用的是**当前**凭证。这个差异本身是真实存在的，报告第 1 章会写出当前窗口与哈希，
   用来说明"我现在依据的是哪一份"。

如果变更是**缩小**了时间窗或范围，注意报告第 4.1 节会把落在新窗口之外的已执行动作
列出来 —— 那不是错误，而是"窗口被动过"的可查痕迹（见 `SECURITY.md` §1.4）。

## 常见错误

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 登记后重新扫描了原件 | 哈希失配，凭证作废 | 只以归档副本为准；要更清楚的版本就另起一份并走变更流程 |
| 用阅读器"另存为"再登记 | 同上 | 直接归档原始下载件，不做任何转换 |
| 把 `.msg` 当长期归档 | 依赖特定客户端，可能打不开 | `.eml` 作为证据本体，PDF 作为可读副本 |
| 邮件打印成 PDF 但丢了头部 | 无法证明发件人 | 打印预览确认含发件人/时间，或改登记 `.eml` |
| `document` 路径按当前目录写 | 核验报"文档不存在" | 路径相对**凭证文件所在目录** |
| 把归档副本提交进公开仓库 | 泄露客户机密与签名 | `.gitignore` 排除；只提交哈希 |
| 归档副本只存本机一处 | 硬盘故障 = 证据消失 | 加密存储 + 备份；报告里的哈希仍可佐证 |
| 覆盖已有归档副本 | 作废已登记哈希 | 脚本会拒绝覆盖；变更请换文件名 |
| 把哈希当成"签名" | 高估证据力 | 哈希只证明"此后未变"；真实性靠授权方 |
| 让客户肉眼比对 64 位哈希 | 复核变成走过场，或抄错一位后误判 | 用 `verify-report.mjs` 一条命令，看退出码 |
| 用 `diff` 比对两份文件 | 只能看出差异，无法证明"是不是同一份" | 哈希才是判据；`diff` 只用于排查差异内容 |
| 授权书缺排除项就开测 | 真出事 | 回第 0 步补齐；含混的授权不是授权 |

## 能力边界（写进交付说明）

哈希登记能证明：

- ✅ 报告所依据的那份文件，与归档副本**逐字节相同**
- ✅ 文件自登记之后**没有被改动过**
- ✅ 客户可以独立复核（拿原件算一次哈希即可）

哈希登记**不能**证明：

- ❌ 授权书本身是真实的、未被伪造
- ❌ 签署人确实有权处置那些资产
- ❌ 授权书覆盖的资产确实属于签署方（客户常不清楚自己的资产边界）
- ❌ 测试过程中没有发生日志之外的行为（见 `SECURITY.md` §1.3）

**因此**：哈希登记消除的是"文件被换过"这一种不确定性，
它把"我依据的是这份授权"从陈述变成事实 —— 但"这份授权有效"仍需授权方确认。
把这句边界一并写进交付说明，比让客户误以为工具能代替法律判断要负责得多。
